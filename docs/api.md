# API reference

Every entry point of `@duongtdn/agent-cockpit`, with its exports, options,
operations and events, and every `CockpitError` code. For the concepts behind
them, read the [guide](guide.md).

**Status:** the first operations are built: creating and mounting a cockpit,
the units of work (running a job in every state of its key's session,
sending, opening, starting over, their records, the cap, the jobs'
descriptions and choices), following the sessions, the
browser's client and terminal, and access: opening beyond loopback, the
app's token on its own routes and its renewal, and the failures the app is
told of, and the Claude Code driver, complete: its options, a job's
driver part, the agent's version, the start-up dialogs, failed turns,
background tasks and compaction. This reference lists exactly what the package
exports today; a test compares the export tables and the error
table below with the code, so they cannot drift apart.

## Entry points

One package, six entry points, one version: an app's server code and browser
code always match. The browser entries never pull server code into a bundle,
and the channel entry is safe to import on both sides.

Each entry's table lists every export. The kind is `class`, `function`,
`constant` or `type`.

### `@duongtdn/agent-cockpit/client`

Runs in the browser: the framework-free client. It takes the app's token from
the page's link (`#cockpit=…`), removes it from the address bar and keeps it
in the origin's local storage, then sends it with every request (in the
`cockpit-token` header) and every WebSocket (as a subprotocol), never in a
URL. The token is the page's: every client and terminal of the page has it,
whichever took it from the link, and keeps it in memory when the browser
refuses the page its storage. A link opened later in the page's own tab
(`hashchange`: a link pasted into an open tab changes only the fragment) is
taken the same way, and the page's streams and terminals reconnect with it
at once. Without a valid token the server refuses every call with
`no-token`.

| ---------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `createCockpitClient`  | function | `createCockpitClient({ baseUrl })` creates the client; `baseUrl` is where the app mounted the cockpit (a path or an HTTP URL). ## Mounting

`cockpit.handle(req, res)` and `cockpit.upgrade(req, socket, head)` take
`node:http` objects. They are mounted: the app gives them only the requests
under its prefix, with the prefix removed from `req.url`, and every path they
are given is the cockpit's. `cockpitFastify` does that for Fastify; on a
plain `node:http` server the app tests the prefix and removes it itself (the
[guide](guide.md#getting-started) shows how). The client's and the
terminal's `baseUrl` is that prefix. There is no `prefix` option.

Every request and WebSocket upgrade the handler is given passes the request
checks before anything else. It is refused with `refused` when it comes from
beyond the loopback (`cause: 'remote'`), carries `Forwarded`,
`X-Forwarded-For` or `X-Real-IP` (`'forwarded'`), reaches a local address
other than `127.0.0.1` or `::1` (`'local-address'`), or names a `Host` or an
`Origin` other than `127.0.0.1` or `localhost`, any port, or one of the
app's `origins` (`'host'`, `'origin'`); then with `no-token` when it does
not carry the app's token. With `authorize`, a remote request (from beyond
the loopback, or with a forwarding header) passes the `Host` and `Origin`
checks, then is served only when `authorize` resolves `true`, with no token,
and is refused with its own cause otherwise; a local request still needs the
token and never reaches `authorize`. The `terminal` switch then applies to
the terminal's path (`'terminal-off'`). [Security](security.md) has the
whole of it.

Under the mount the cockpit serves its own wire, which the client and the
terminal speak; an app never calls it, and it may change from one version to
the next. Its paths, for the app's logs and proxy:

| Path               | Method    | What it is                                                                                                                                                 |
| ------------------ | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/run`             | `POST`    | Runs a job: the client's `run`.                                                                                                                            |
| `/send`            | `POST`    | Sends a prompt to a unit of work: the client's `send`.                                                                                                     |
| `/open`            | `POST`    | Opens a unit of work: the client's `open`.                                                                                                                 |
| `/jobs`            | `GET`     | Describes the jobs: the client's `jobs`.                                                                                                                   |
| `/options`         | `POST`    | Reads a field's choices: the client's `options`.                                                                                                           |
| `/sessions`        | `GET`     | Lists the sessions.                                                                                                                                        |
| `/follow/sessions` | WebSocket | Follows the sessions.                                                                                                                                      |
| `/terminal/<key>`  | WebSocket | A session's terminal (the pty bridge).                                                                                                                     |
| `/terminal/<key>`  | `GET`     | The terminal's probe: the same checks and the terminal's switch, answered 426 when they pass; the terminal asks it to tell why its WebSocket did not open. |

A path the cockpit does not know is answered 404, and an upgrade to one is
refused and its socket ended; it never falls through to the app. A known
path asked with another method is answered 405 (with `Allow`), a WebSocket's
path asked as a plain request 426, a body over 1 MiB 413. A `CockpitError`
is answered with the HTTP status of its code (see [Errors](#errors)) and the
error as JSON, `{ "error": { "name", "code", "message", …fields } }`; any
other failure with 500 and no body, which the client reports as
`unreachable`. No answer may be cached (`Cache-Control: no-store`). The
token travels in the `cockpit-token` header and, on a WebSocket, in a
subprotocol; never in a URL.

| `otherMcpServers`   | `true`                                 | `false` keeps every MCP server but the cockpit's out of the sessions (`--strict-mcp-config`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `sandbox`           | none: the person's own settings decide | `true`, or `{ excludedCommands?, allowUnsandboxedCommands? }`: runs every session in the agent's sandbox, with these exceptions. It only turns the sandbox on: `false` is refused. Each session's settings then carry `sandbox.enabled` and `failIfUnavailable`, so the agent stops rather than run unsandboxed; before each launch the driver looks for what the sandbox needs on the agent's `PATH` (on Linux, `bwrap` and `socat`), then has `bwrap` make the nested user namespace the agent's sandbox makes (once per `bwrap` while it passes, bounded to 10 seconds), and refuses the launch with `sandbox-unavailable` when either fails. `excludedCommands` run outside the sandbox, unconfined; `allowUnsandboxedCommands: true` lets a command the sandbox refuses run outside it once the person approves (`false` when left out). [Security](security.md#the-sandbox-an-app-asks-for). |

Any other option is refused with `invalid-options`, never ignored. The driver
launches `claude` from the `PATH` of the server's environment (without the
app's `hiddenEnv`), without the variables Claude Code sets for the programs
it runs (`CLAUDE_CODE_*`, `CLAUDECODE`), so a server started from a Claude
Code terminal does not hand that session's to its agents. The `env` of the
person's own Claude Code settings still reaches the agent, which applies it
itself: a provider set there (Bedrock, a base URL) keeps working. Each session's settings and its token are
written in the cockpit's state folder, readable by the app's user alone;
the token is never on a command line or in the environment.

Every session's settings also carry, whatever the app sets, the lines that
keep the agent from the cockpit: a `Read` and an `Edit` deny on each state
root, after the app's own denies; an `Edit` deny on the files the
cockpit can name that start code at the agent's next launch
(`.claude/settings.json`, `.claude/settings.local.json` and `.mcp.json`
wherever they are, and every file of a `.claude/hooks`, `.claude/agents`
or `.claude/skills` folder; the person's own `settings.json`, the legacy
`.config.json` and every `.claude*.json` in the agent's configuration
folder, every `.claude*.json` in the home, and their `plugins`, `agents`
and `skills` folders), so that in a cockpit session the agent can never
edit one, even when asked (in `acceptEdits`, `auto` and `bypassPermissions`,
where the agent's file tools write unasked and act as the person, they are
defense in depth, not a boundary); the app's
ports denied to the sandbox's network on every local address and loopback
name; the agent-facing listener allowed; and no command let out of the
sandbox (unless the app's `sandbox` allows it). They do not turn the
sandbox on: without the app's `sandbox` that stays the person's choice,
and without the sandbox its lines change nothing.
[Security](security.md#keeping-the-agent-out) says what each line keeps
out. A launch whose environment names a `CLAUDE_CONFIG_DIR` or a `HOME`
those denies could miss (relative, or holding a character a permission
rule reads as its own) is refused with `invalid-options`, as
`createCockpit` refuses the server's.

### `claudeCode.job(part)`

Builds a job's driver part, which the job carries as `driver`. Each field
is optional:

| Field            | What it does                                                                               |
| ---------------- | ------------------------------------------------------------------------------------------ |
| `permissionMode` | The mode the job's sessions are launched in, in place of the driver's.                     |
| `permissions`    | Rules added after the driver's, list by list: the driver's deny and ask rules always hold. |
| `model`          | The model of the job's sessions, over the driver's and the person's.                       |

Anything else (the plugin, the sources of settings, the sandbox, the
acceptance of an open mode) stays the app's, and is refused with
`invalid-options`, as is a part that does not fit. A part whose mode is
open is checked as the driver's own mode is (see `authorize`).

## Operations

`cockpit.run`, `send`, `open`, `jobs` and `options`, in the app's server and
in the browser's client alike, act on the units of work (see [Units of
work](#units-of-work)). A run checks the arguments against the job's schema
(`unknown-job`, `invalid-arguments`) and derives the key (`invalid-options`
when the job's `key` gives no `[a-z0-9-]+` of 100 characters at most: a
key names a tmux session, a folder and a file of the state folder). A call that
launches the agent (a run, an open, a send to an `ended` session) resolves
once the session leaves `starting`: `state: 'busy'` once the agent took the
prompt, `state: 'idle'`
for a job without one, `state: 'waiting'` while a start-up dialog waits for
the person in the terminal (`pending: [{ kind: 'terminal', dialog }]`; a
first prompt too long for the command line settles the call only once it
is typed, see [Units of work](#units-of-work)),
`state: 'ended'` when the agent exited before it reported (`reason:
'declined'`, with its `dialog`, when the person left a dialog).

Before each launch the driver reads the version of the agent the launch
would run: the first executable `claude` on the launch's `PATH`, asked
`claude --version` once per executable (by its real path and its time of
change, so an update is read anew). None found is refused with
`agent-not-found`, and so is one that cannot be run: it fails
`--version`, does not answer within 10 seconds, or prints no version (the
message says why; `cause`, the server's alone, holds what it printed; a
failure is not kept, so the next launch asks again). One older than the
driver's tested range is refused with `agent-too-old`, nothing listed; a
newer one, or a build with a suffix (`2.1.340-beta`) not older than the
range, runs, and `on('untested-version')` tells it once per version.
`status()` follows each reading, and the one `createCockpit` takes.

A launch whose app asked for the agent's sandbox (`claudeCode({ sandbox
})`) where its programs are missing, or where `bwrap` cannot make the
nested user namespace the sandbox needs (an AppArmor-confined `bwrap`),
is refused with `sandbox-unavailable`.
Where the agent finds the sandbox unavailable in another way, it stops
after its first hook (`failIfUnavailable`): the run resolves `ended`, the
session's `reason` `lost`, and no prompt was sent. A job's driver part is
checked again as the run launches it (`invalid-options`).

A launch while no port of the app's browser-facing server is known (no
`port`, and no adapter that read one) is refused with `no-app-port`.

Until its first hook, the cockpit reads the agent's screen (every 250 ms):

- A start-up dialog (the folder's trust, the warning of
  `bypassPermissions`, the first run's onboarding, the login) makes the
  session `waiting`, `pending: [{ kind: 'terminal', dialog }]`; a panel
  that waits for a key and has no name the driver knows (the question
  about a custom API key) waits the same way, with no `dialog`. The person
  answers it in the terminal; the session is `starting` again once the
  agent goes on, and its `since` stays while one dialog follows another.
  The person who leaves a dialog ("No", or Esc) ends the session
  `declined`, with its `dialog` when the driver knew it; the next launch
  meets the same dialog.
- With no dialog on screen, the agent has 10 seconds from its launch, or
  from the moment a dialog left the screen, to send its first hook, and 5
  seconds once its input box shows (an agent whose hooks are all turned off
  shows the box and nothing else). Otherwise the session is ended and the
  run refused with `unobservable`.

A launch prompt the agent takes without a turn, a local command such as
`/clear`, `/context` or an unknown name, fires no hook: the agent writes
the command's end into its conversation (for `/clear`, the new one), and
the cockpit reads it there (within half a second): the session is `idle`.
A command that opens a panel (`/help`, `/cost`, `/status`, `/config`,
`/model`) writes nothing while it shows: the cockpit reads the screen from
the agent's first hook on, the panel makes the session `waiting`,
`pending: [{ kind: 'terminal' }]`, and the panel closed (the input box
back, the agent showing no work above it) makes it `idle`. A screen the
driver does not know, shown 5 seconds after the agent's first hook, is
taken for a panel it has no name for: `waiting` the same way, for the
person to look. The input box alone tells nothing (the agent draws it
before it takes the prompt), nor does the box while the agent works: the
session stays `starting`, never guessed `idle` or `busy`, and the agent's
next hook or entry tells the rest.

A session follows the conversation the agent works in: the one launched,
or the one it moves to (Claude Code's `/clear` starts a new conversation
under a new id, which its `SessionStart` names). What the cockpit reads
of the conversation outside the hooks (an interruption, a compaction), and
an ended session's `canResume`, follow the new one; an interruption
recorded in the conversation left just before the move still ends the
turn open then. A compaction begun while `idle` returns the session to
the `idle` it left when it ends (`PostCompact`), when it fails (Claude
Code's `StopFailure` of the compaction's own agent, told from a
background task's by the tasks the session's hooks named), and when a
person interrupts it, which no hook tells: the agent then writes the
command's end alone into its conversation, where the cockpit reads it.
No screen is read for a compaction. An interruption the agent recorded
before the next prompt was taken ended the turn before, and leaves the
new one `busy`.

### Units of work

A unit of work is a key's conversation and its record, kept in the state
folder (`records/<key>.json`, readable by the app's user alone) until the
app removes it, loaded at `createCockpit`. Calls on one key run one at a
time, in the order they were asked, each on the state the one before left:
a second run while the first launches waits for it, then meets the session
it left (`wrong-state` on a `busy` one). A call whose long first prompt
waits behind a start-up dialog lets the calls after it run meanwhile (see
below). Nothing waits for a session to
become `idle`. A run's arguments, key and prompt are checked as it
is asked, before it waits.

A session the cockpit is ending (the cap making room for another key's
launch) takes no send and no run until it is gone: `wrong-state`, its
state as it was, the message saying the cockpit is ending it. Its agent
is still heard meanwhile.

`run(jobId, args, { fresh? })` checks the arguments against the job's
schema, then each value against its field's option source, called with the
other arguments (`not-a-choice`, `field`, `value`; a field whose source only
suggests takes any value), and the job's folder (`directory(args)`,
relative to the app's folder, resolved with every link followed: outside
the app's real folder `folder-outside-app`; made when missing; the agent
launched in its real path; another folder than the one the key's record
keeps `folder-changed`, `recorded`, `computed`, unless the run starts a
new conversation, which records the job's folder anew). The job's driver
part is checked again, as `createCockpit` checks it (`invalid-options`;
an open mode refused in a cockpit opened beyond loopback without
`acceptOpenNetwork`). It then acts by the state of the key's session:

| State                         | Run                                                                                                                                                                                                                                                      |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| no record                     | Starts the agent with the prompt: `started`.                                                                                                                                                                                                             |
| `ended`                       | Resumes the conversation with the prompt: `resumed`. A job with `fresh: true` starts a new one (`started`, `fresh`); a conversation the agent no longer keeps is started anew (`started`, `conversation-gone`).                                          |
| `idle`                        | Types the prompt, the person's draft kept: `sent`. A session launched with other settings (another job of the key, or the job changed) is ended (`reason: 'restarted'`), then resumed with the run's settings and prompt: `resumed`, `settings-changed`. |
| `starting`, `busy`, `waiting` | Refused `wrong-state`, with the state (and `pending`).                                                                                                                                                                                                   |

A job without a prompt starts or resumes with none and resolves at `idle`;
on a live session it has nothing to send (`nothing-to-send`, with the
state), but for an `idle` session launched with other settings, which it
restarts (`resumed`, `settings-changed`). With `{ fresh: true }`, the run
starts a new conversation (`started`, `fresh-on-request`): an `idle`,
`busy` or `waiting` session is ended first, `starting` refused. A session is ended gracefully (for
Claude Code, SIGTERM, then a kill after 5 seconds), its conversation kept;
a turn under way is not interrupted first, and its partial answer is lost.
A launch that ended a session (a fresh start, a restart on other settings)
lists the background tasks it stopped (`stoppedTasks`). The old
conversation stays in the record's `earlierConversations`, and so does one
the agent moved to before the launch ended it (a `/clear` told while the
run waited for its turn), in the order they were left.

Each run that started, resumed or typed its prompt (`sent`) is kept in the
key's history (`operation: 'run'`, its `jobId` and `args`, `at`, its
`action` and `reason`, the `conversationId` it acted in); one with nothing
to send, refused, or failed with its session live (a first prompt not
taken), is not. The history keeps a run's `args` as the run was given
them at the call (copied then: a change the caller makes to its object
afterwards is not recorded), the schema's input: what the schema gives (a number from a text, a
path it resolves) stays out of the record and the pages, and an open or a
send reads them through the schema again.

`send(key, prompt)` types the prompt into an `idle` session (`sent`), its
settings kept; an `ended` one is resumed with the prompt and the settings of
the key's last run (its job as the app defines it now, with its recorded
arguments, every check of a run made again): `resumed`, or `started`,
`conversation-gone`. A key with no record is refused `unknown-key`; a last
job gone `unknown-job`; `starting`, `busy`, `waiting` `wrong-state`. A
send has no `fresh` and is not kept in the history: the next open, or send
to an `ended` session, still launches with the settings of the last run.

`open(key, { fresh? })` resumes an `ended` session with no prompt and the
settings of its last run, resolving at `idle` (or `waiting` at a start-up
dialog): `resumed`, or `started`, `conversation-gone`. A live session, or a
key with no record, has nothing to open (`nothing-to-open`, with the state
when there is one). With `fresh`, a new conversation (`started`,
`fresh-on-request`), a live session ended first. The open is kept in the
history.

A prompt that is empty or only whitespace (blanks, line breaks and
U+2063, which the agent trims to nothing) is refused `invalid-arguments`,
its issue at `prompt`, and one over 100,000 characters (code points)
`prompt-too-long` (`length`, `max`), before anything, by a run and a send
alike. A launch passes its prompt on the agent's command line; one
too long for it (for Claude Code, over 120,000 UTF-8 bytes) is typed once
the agent reported its start and drew its input box (waited for 5
seconds at most, a start-up dialog's time not counted). The page's
terminals' keys are held (`held`) from the agent's start (its
`SessionStart`) until the prompt is typed. A start-up dialog in place of
the box lets them through for the person to answer it, and drops the keys
kept until then, never typed: typed toward the box, they would answer a
dialog the person had not seen (the terminal's wire tells its browser
with the release, `released` carrying `discarded: true`); they are held
again once the box shows. The session stays `starting` until the agent
takes the prompt, and the call settles then (`busy`, or `ended`).

A dialog shown first makes the session `waiting`: the prompt is typed
once the person answered it, and the call stays pending until then, but
nothing waits on the key meanwhile. The session is recorded at once, and
the calls asked after it act on the `waiting` session as the run table
says: a run or a send is refused `wrong-state` (with the dialog in
`pending`), an open has nothing to open (`nothing-to-open`), a job
without a prompt nothing to send (`nothing-to-send`), and a `fresh` run
or open ends the session. Whatever ends it (those, or the agent exiting),
the pending call settles `ended`, its entry kept in the key's history;
so too when the dialog shows once the agent started, in place of its
input box. What became of
the prompt shows in the session's state: `busy` when the agent took it,
`idle` when not. The pending call's entry in the key's history goes in
the order the calls were asked. Not taken, no box drawn, or the session
no longer `starting` once the box shows (nothing typed then), the call
rejects as a send does (`prompt-not-taken`, `wrong-state`), the session
`idle` when it was still `starting`; the unit of work is recorded all the
same, but the run is not kept in the key's history.

A prompt is typed into the input box keeping what the person left there:
the draft is stashed, the prompt typed (tabs as four spaces, control
characters left out, a leading `!` after a space; a leading `/` is a
command), Enter pressed until the agent says it took it (three times at
most; `prompt-not-taken` otherwise, the box cleared), and the draft put
back. The page's terminals' keys are held meanwhile (their status `held`)
and passed on after. A box that shows an entry the person recalled from
the prompt history (Claude Code's `History n/m`) is not typed over: the
send fails `wrong-state`, nothing typed. Before every write the cockpit
checks that the session still shows its input box and that nothing but the
prompt's own turn began: otherwise the send fails `wrong-state` with the
state the session is in. What was typed is then cleared and the draft put
back while the input box still shows and the agent has used no tool since
the send began (a tool may ask, its dialog drawn over the box a moment
later); otherwise (a key could answer the dialog) nothing more is typed, and the error's
message says the draft is in the input box's kill ring and which keys bring
it back (Ctrl+Y, or Ctrl+Y then Alt+Y). A prompt the agent took counts as
sent even when its turn drew a dialog before the draft was back.

`jobs()` describes each job for a page's form: `{ id, title, description?,
schema, options, hasPrompt }`, its schema as JSON Schema (the input it
takes, each field's `label` and `hint` kept), `options` naming each field
with a source as `'choices'` or `'suggestions'`; never the job's key,
prompt, folder, `fresh` or driver part. `options(jobId, field, argsSoFar?)`
reads a field's choices, the arguments filled so far checked against the
schema made partial (`invalid-arguments`); a field with no source is
`invalid-arguments`. On the wire: `POST /run` (`{ jobId, args, fresh? }`),
`POST /send` (`{ key, prompt }`), `POST /open` (`{ key, fresh? }`), `GET
/jobs`, `POST /options` (`{ jobId, field, args }`); a body that does not fit
is `invalid-arguments`.

A key whose tmux session was left by an earlier process of the app (the
sessions go on when the server stops) cannot be launched: the launch
rejects with an error that is not a `CockpitError`, answered 500 on the
wire, which the client reports as `unreachable`. There is no interrupt,
end or remove yet.

`cockpit.sessions.list()` gives each session's key, state, `since`, what
its state carries and its `record` (`conversationId`,
`earlierConversations`, `history` of its runs and opens), in the order
their keys were first recorded; a recorded key with no live session is
`ended` (`lost` when it was recorded before the server started);
`cockpit.sessions.follow(handler)` gives that list at once, then at every
change, and returns a function that stops. A session that ends is seen
within a second. The client's `sessions.follow` gives the same list.

## Events

The sessions' and the asks' events are not built yet. What is:

- `cockpit.on('error', handler)`: each `internal-failure` (see
  [Errors](#errors)).
- `cockpit.on('untested-version', handler)`: an `UntestedVersion`, the
  first time a launch runs a version of the agent newer than the driver's
  tested range, or a build with a suffix not older than it, once per
  version; what a handler throws goes to
  `console.error`, and the launch goes on.
- `client.on('error', handler)` and `terminal.on('error', handler)`: why a
  live stream or a terminal could not connect (`no-token`, `refused` with
  its `cause`, `unreachable`), once per failed attempt.
- A client's or a terminal's handler that throws stops neither the other
  handlers nor what the cockpit does next, a reconnection among them: what
  it threw goes to `console.error`.
- `terminal.on('status', handler)`: the terminal's status.

## Errors

Every error the cockpit throws or rejects with, on the server and in the
client alike, is a `CockpitError`: an `Error` with a kebab-case `code`, a
`message` in English for logs and developers (the app words its own for the
person), and the fields of its code. The code decides the fields, so
`switch (error.code)` narrows them in TypeScript. "Nothing to do" is never an
error: an operation says so in its result.

The table below says what each code is for; some belong to operations not
built yet.

```ts
import { isCockpitError } from '@duongtdn/agent-cockpit/client';

try {
  await somethingThatMayReject();
} catch (error) {
  if (!isCockpitError(error)) throw error;
  switch (error.code) {
    case 'wrong-state':
      showState(error.state, error.pending);
      break;
    case 'invalid-arguments':
      showIssues(error.issues);
      break;
    default:
      showFailure(error.message);
  }
}
```

`new CockpitError(code, message, fields)` creates one; an app rarely needs
to. Any error may also carry `cause`, the error that lies under it; on
`unobservable`, `sandbox-unavailable` and `refused`, `cause` is a field of
the code instead.

The fields are properties of the error itself. `JSON.stringify(error)` keeps
its `name` (`'CockpitError'`), `code`, `message` and the fields of its code;
it leaves out the stack and the error that lies under it.

A field marked `?` is optional. "A launch" is anything that starts the
agent: a run, an open, or a send to an ended session. "HTTP" is the status
the handler answers the code with, for logs, proxies and a network panel;
the client reads the error from the answer's body alone. The codes of
creating the cockpit, of the one-shot call and the client's own
`unreachable` are never raised by a request; the table gives the status
they would have.
